# Hot Springs "Near Me" Query Optimization — Spec

**Scope:** Soak Trail (hub + 6 regional sites). Originated as a SoakColorado Asana task; generalized to the whole network.
**Status:** Proposal for review — no code changed yet.

---

## 1. Objective

Win organic and AI-answer-engine citations for **"hot springs near me"** (and its variants: "hot springs nearby", "closest hot spring", "hot springs near my location", "free hot springs near me", "hot springs camping near me").

Because "near me" is a *location-dependent* query, the goal decomposes into one concrete, measurable outcome:

> **For every city or town where a real user might search, there is a dedicated, crawlable, schema-rich landing page that Google and AI systems can surface when they resolve "near me" to that place.**

---

## 2. Why "near me" is different

1. The search engine (or AI system) replaces "near me" with the searcher's resolved location (GPS/IP) before ranking.
2. There are two surfaces to win:
   - **Classic SERP** — local pack + organic. We are a national content network with **no physical business listing**, so we cannot appear in the Google local pack. We *can* win the organic result for "hot springs near [city]".
   - **AI answer engines** (ChatGPT/Perplexity/Gemini/Copilot) — these localize too, and cite passages from pages. This is where our schema + self-contained copy already performs (see `docs/AI-SEO-UPDATES.md`).
3. Therefore the whole strategy is a **coverage play**: maximize the number of place-specific landing pages, and make each one maximally extractable.

Strategic thesis:

- The people who actually search "hot springs near me" are often **in small mountain/desert towns next to a spring** (Salida, Buena Vista, Glenwood Springs, Pagosa Springs, Ouray), *not* in a 2M-person metro. Our current hub coverage is inverted: it covers the top-100 metros and skips the small towns that matter most.
- The regional domains (`soakcolorado.com`, `soaktherockies.com`, …) have the topical authority for "Colorado/Idaho/Washington hot springs" — they should own their region's near-town pages, not just the hub.

## 5. Target architecture

### 5.1 One canonical data model

Normalize to a single, shared shape (city/town → springs), generated once and consumed by both hub and regional sites:

```jsonc
// city slug -> page data  (city-towns, not just metros)
{
  "buena-vista-co": {
    "city": "Buena Vista",
    "state": "co",
    "state_name": "CO",
    "region": "colorado",           // which regional site "owns" this town
    "lat": 38.8422,
    "lng": -106.1311,
    "population": 3010,
    "slug": "buena-vista-co",
    "count": 6,
    "springs": [
      {
        "slug": "cottonwood-hot-springs",
        "name": "Cottonwood Hot Springs",
        "state": "co",
        "region": "colorado",
        "distance_mi": 7.4,
        "temperature_f": 104,
        "access_type": "resort",
        "site_url": "https://www.soakcolorado.com"
      }
      // …sorted by distance_mi ascending
    ]
  }
}
```

Derive the **town list from the regional `near_cities.json` files first** (they already contain the spring-adjacent small towns), then top up with the SimpleMaps metros. Drop or lower the `MIN_POPULATION` floor and raise/remove `MAX_CITIES_TOTAL`.

### 5.2 Page model — one template, two tiers

**Tier 1 — Hub (`soaktrail.com/near/[city]`):** keep the existing rich template, expand its input to the full town set. These are the national long-tail pages.

**Tier 2 — Regional (`soakcolorado.com/near/[city]`, etc.):** bring the regional near page **up to parity** with the hub template:

- `ItemList` (springs with `geo` + distance + temperature)
- `Place`/`GeoCoordinates` for the city
- `FAQPage` (4 self-contained Q&As, same pattern as hub)
- Definition-block opening paragraph ("X natural hot springs within 50 miles of [City], [State]…")
- `BreadcrumbList`
- "Last updated" freshness signal

Reuse the existing helpers in `packages/shared/src/lib/schema.ts` rather than reimplementing.

### 5.3 Geolocation UX (new)

Add a location affordance to **both** the locator and the near pages:

1. **Client:** "Use my location" button → `navigator.geolocation.getCurrentPosition()` → reverse-match to nearest covered city → redirect to `/near/[city]` (or re-center the map + surface nearest pins on `/locator`).
2. **Server fallback (no JS / denied permission):** read Cloudflare geolocation headers already available on Pages (`CF-IPCity`, `CF-IPLatitude`, `CF-IPLongitude`, `CF-IPCountry`) to resolve the city and pre-render/redirect. This makes the "near me" behavior work for crawlers-less real users and for server-rendered entry.
3. **Permalink-ability:** geolocation never replaces the crawlable city pages — it *routes to* them, so `soaktrail.com/near` remains a fully indexable hub and `/near/[city]` remains the canonical landing surface.

### 5.4 Indexation & sitemaps

- **Hub:** already correct; extend `sitemap-near.xml.ts` automatically by regenerating `cities_index.json`.
- **Regional:** add a dynamic near-page sitemap (mirror of hub's `sitemap-near.xml.ts`), and switch near pages to `prerender = true` with `getStaticPaths()` (they're build-time static data — no reason to SSR). Reference the new sitemap from each regional `astro.config.mjs` (or a dedicated `sitemap-near.xml.ts` route if `@astrojs/sitemap` can't add dynamic routes).
- Add a **`/near` directory hub per regional site** (grouped by region/state) so the near pages are internally linked and discoverable, not orphaned.

### 5.5 Internal linking & canonical mapping

- Hub `/near/[city]` ↔ regional `/near/[city]` should cross-link (hub links "full [Region] guide → soakcolorado.com/near/[city]"; regional links "all cities nationwide → soaktrail.com/near").
- Regional `/near` hub in the site nav.
- On spring detail pages, keep/strengthen "Nearest Towns" links (already present in `soakcolorados/springs/[slug].astro`).
- Where a hub page and a regional page target the **same city+state**, pick one canonical (recommend: regional owns its own towns; hub owns metros and towns not in any region) to avoid duplicate-content dilution.

### 5.6 AI citation

Near pages are already the highest-intent AI surface (`docs/AI-SEO-UPDATES.md` §4). Extend the three AI signals to the **regional** near pages and to the new small-town pages:

1. **Definition block** as the first sentence (already the hub pattern).
2. **Self-contained FAQ answers** ("There are 6 hot springs within 50 miles of Buena Vista…") — directly quotable.
3. **Specific numbers everywhere** (count, distance, temperature) — what AI systems quote.

## 6. Implementation plan

### Phase 0 — Data pipeline (foundation)

1. Extend `scripts/build_near_city_pages.py`:
   - Accept an explicit town-list input sourced from the regional `near_cities.json` files (small towns first).
   - Lower `MIN_POPULATION` (e.g. `0` or `500`) and raise `MAX_CITIES_TOTAL` (e.g. `500`+).
   - Emit the canonical `city→springs` shape with a `region` field per town.
   - Add a `--site <slug>` filter so the same script can emit per-region town data.
2. Regenerate `sites/soaktrail/src/data/near_city_pages.json` + `cities_index.json`.
3. Emit per-region town files for each regional site (replacing/augmenting the ad-hoc `near_cities.json` where applicable).

**Acceptance:** hub coverage jumps from 100 metros to hundreds of towns, including the spring-adjacent small towns; every town carries a `region`.

### Phase 1 — Regional near-page parity (start with SoakColorado, then replicate)

4. Upgrade `sites/soakcolorados/src/pages/near/[slug].astro`:
   - `prerender = true` + `getStaticPaths()`.
   - Add `ItemList`, `Place`/`GeoCoordinates`, `FAQPage` (reuse `packages/shared` helpers).
   - Add definition-block intro + "last updated" + author attribution.
5. Add a `sites/soakcolorados/src/pages/near/index.astro` directory hub.
6. Add a regional near sitemap and register it.
7. Add `/near` to the nav.
8. Replicate to the other 5 regional sites (shared component/template lives in `packages/shared`).

**Acceptance:** every regional site has schema-rich, indexed, internally-linked near-town pages.

### Phase 2 — Geolocation UX

9. Add "Use my location" to `LocatorMap.jsx` (browser geolocation → recenter + nearest-pin list).
10. Add server-side IP fallback on `/near` and `/locator` using Cloudflare `CF-IP*` headers → redirect/prefill nearest city.
11. Reverse-geocode lat/lng → nearest covered city slug (reuse the `haversine` helper in `scripts/lib/haversine.py` logic, ported to TS for the edge).

**Acceptance:** a permission-granting user lands on a personalized `/near/[city]`; a no-JS/permission-denied user still gets an IP-localized suggestion.

### Phase 3 — Hub expansion & cross-linking

12. Rebuild hub `/near` index + sitemap with the expanded town set.
13. Add hub ↔ regional cross-links and canonical mapping (per §5.5).
14. Re-run the AI-visibility monitoring checklist (below).

## 8. Risks, decisions, open questions

1. **Duplicate content** between hub and regional near pages for the same town — resolve with a clear canonical policy (§5.5).
2. **SimpleMaps licensing** — currently CC BY 4.0; the small-town data comes from our own `near_cities.json`, so no new licensing concern.
3. **Build size** — hundreds of prerendered near pages × 6 sites increases build time; confirm `prerender = true` is acceptable vs SSR (the hub already prerenders 100+ pages fine).
4. **Geolocation accuracy** — browser GPS is precise but permission-gated; Cloudflare IP city is coarse (~city/metro). Use IP only as a fallback and never as a claimed-precision result.
5. **Which towns qualify** — decide the minimum: any town with ≥1 spring within 50 mi, or impose a tiny population floor to filter census artifacts (recommend: ≥1 spring + pop ≥ 500).
6. **Slug mismatch** (documented in `ARCHITECTURE.md`) — near pages deep-link to `{site_url}/springs/{slug}`; the colorado/desert/alaska slug mismatches will 404. Fixing the MCP/D1 slug canonicalization should be sequenced alongside this work so near-page links don't point at broken regional pages.
